A plugin is an extension, plus a little more.

Add a browsa block to a normal Manifest V3 extension. Other browsers ignore it, so the same plugin still works anywhere else. Point at a key to see where it lands.

{
  "manifest_version": 3,
  "name": "Localhost Radar",
  "background": { "service_worker": "bg.js" },
  "browsa": {
    "sidebar": { "page": "sidebar.html" },
    "panel": { "page": "panel.html" },
    "commands": [{ "title": "Open all servers" }],
    "agentTools": [{ "name": "radar_list" }],
    "badges": true
  }
}

SpecBrowsa reads the browsa block today, and its built-in tools (Notes, Agents) already plug into the window this way. The runtime that lets your plugin do the same is still being built, so details may change.

Talking to Browsa.

Plugins send native messages to a built-in host, app.browsa. Each part of the browsa block is a permission people see before they add it, and plugins never run native code.

Let agents use the real browser.

Turn on Settings › Agents and Browsa listens on 127.0.0.1 for MCP. Copy the token from Settings and add it to your agent.

tabs_listtab_openpage_navigatepage_readpage_screenshotpage_clickpage_typepage_evalnotes_listnotes_addnotes_replynotes_resolve
  • Visible. Agents open pages in an Agent space, and every call shows in the Agents panel.
  • Asked once per site. Localhost never asks, and page_eval only runs on localhost.
  • Stoppable. Stop refuses everything that changes a page until it's resumed.
  • Local only. A bearer token is required, and requests carrying a web page's Origin are refused.

How extensions load.

Browsa uses Apple's WKWebExtension. It downloads and unpacks store extensions itself, checks for updates once a day, and asks again when an update wants more permissions. Chrome APIs WebKit doesn't have are filled in natively.

Extension frames
When a page loads an extension's own frame, like an inline menu, WebKit stops that extension's background a few seconds later in third-party browsers. Content scripts are fine. Reported to Apple.
Native messaging to apps
Talking to another company's desktop app needs that app to trust Browsa, so the Safari versions of password managers are the better bet for now.
No API wrapping
Wrapping chrome.* in a JS Proxy stops runtime messages reaching the background, so missing APIs are filled natively, not from script.
Not supported
chrome.debugger, blocking webRequest and DevTools panels. declarativeNetRequest works.
